# OpenCode Agent Guide: Recurring Excel Transformations

This repository implements **one repeatable Excel transformation**. The reusable
comparison and reporting package is the neighboring repository
`../excel-framework-core`.

Use this file as the project instructions for OpenCode and a local Qwen model.
The agent should read this file before changing the project.

## Mission

Given a representative input workbook, a written transformation request, and
preferably a manually verified expected-output workbook, produce a deterministic
Python program that:

1. applies only the requested changes;
2. preserves unrelated workbook content;
3. handles formulas and Excel data types deliberately;
4. rejects input whose relevant structure has drifted;
5. can be run repeatedly without an LLM after development.

The LLM is a development tool only. Production execution must be ordinary,
deterministic Python with no model or network dependency.

## Repository responsibilities

This task repository owns:

- `transform.py`: transformation implementation;
- `run_production.py`: validation gate and quarantine wrapper;
- `docs/SPEC.md`: precise transformation contract;
- `docs/ALLOWED_CHANGES.yml`: whitelist of intentional workbook changes;
- `samples/input.xlsx`: anonymized representative input;
- `samples/expected_output.xlsx`: manually approved result;
- `samples/actual_output.xlsx`: result generated by `transform.py`;
- `tests/`: regression and safety tests;
- `reports/`: generated comparison reports.

`../excel-framework-core` owns generic comparison, validation, configuration,
and reporting code. Put generic improvements there; do not duplicate that code
in this repository.

## Required user input

Before implementation, obtain or locate:

1. A representative, anonymized source workbook.
2. A precise transformation description.
3. Preferably a manually prepared expected-output workbook.
4. Rules for formulas when columns move.
5. Rules for blanks, errors, merged cells, hidden content, tables, and multiple
   sheets when relevant.

If the expected output is absent, the agent may implement from an unambiguous
specification, but must clearly state that verification is weaker. Ask a
question only when different reasonable interpretations would produce
materially different workbooks.

## Agent workflow

### 1. Inspect before editing

- Read `README.md`, `docs/ARCHITECTURE.md`, `docs/SPEC.md`,
  `docs/ALLOWED_CHANGES.yml`, `transform.py`, `run_production.py`, and tests.
- Inspect workbook structure programmatically with `openpyxl`: sheet names,
  used ranges, likely header rows, cell value types, formulas, number formats,
  merged ranges, tables, hidden rows/columns, widths, and frozen panes.
- Do not print confidential workbook contents unnecessarily. Summarize only the
  minimum needed to reason about structure.
- Never modify the user's source or expected-output workbook in place.

### 2. Convert the request into a contract

Replace the placeholders in `docs/SPEC.md` with:

- exact source and output paths;
- sheets and header-selection rules;
- ordered transformation steps;
- formula semantics;
- value-type and display-format semantics;
- invariants and edge cases;
- definition of done.

Update `docs/ALLOWED_CHANGES.yml` narrowly. Prefer exact ranges over entire
columns, and entire columns over entire sheets. Every permission needs a reason.
Do not broaden the whitelist merely to make a failing test pass.

### 3. Implement conservatively

- Use `openpyxl`; do not rewrite the workbook through pandas.
- Load with `data_only=False` so formulas remain formulas.
- Modify the existing workbook rather than reconstructing it.
- Save only to the requested output path.
- Create parent output directories if needed.
- Make the transformation deterministic and safe to rerun on a fresh input.
- Prefer header-based column lookup when upstream column positions may change.
- Detect missing or duplicate required headers and fail with an actionable
  message rather than guessing.
- Preserve native Python/Excel date values when the request concerns display.
  Change `cell.number_format`, not the stored date, unless conversion is
  explicitly required.
- Preserve `None`, formulas, error values, booleans, and numeric values without
  coercing them to strings.
- Do not use `values_only=True` when copying cells that may contain formulas.

### 4. Handle column movement explicitly

Column movement is not just value movement. Consider:

- values and formulas;
- number formats and full cell styles;
- comments and hyperlinks;
- row heights and column widths;
- hidden state and outline levels;
- merged ranges;
- data validation and conditional formatting;
- tables, filters, named ranges, charts, and formulas referring to moved cells.

Before implementing a move, establish the required formula semantics. Moving a
formula string unchanged, copying it with `Translator`, and regenerating it from
logical fields are different operations.

Avoid repeated `insert_cols`, `delete_cols`, or `move_range` calls without first
checking their effects on workbook objects and formula references. For complex
reordering, compute the final column mapping once and copy from a preserved
source representation to avoid overwriting columns mid-operation.

### 5. Test and verify

At minimum:

```bash
python transform.py samples/input.xlsx samples/actual_output.xlsx
pytest
```

Then inspect generated reports under `reports/`. A successful Python exit alone
is not completion.

Add focused tests for transformation rules and edge cases. Tests should verify
important values, formulas, types, number formats, column order, and preservation
requirements directly, not solely through the generic comparator.

If dependencies are missing during local co-development:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ../excel-framework-core
pip install "openpyxl>=3.1.0" "pytest>=8.0"
```

Do not commit virtual environments, confidential workbooks, or generated review
cases.

### 6. Production handoff

The routine command is:

```bash
python run_production.py path/to/incoming.xlsx path/to/output.xlsx
```

Explain that exit code `0` means validation passed and transformation ran. Exit
code `1` means detected drift caused quarantine under `needs_review/`; the input
was not transformed.

Handoff must state:

- what was implemented;
- exact execution command;
- assumptions and supported input shape;
- tests executed and their result;
- report locations;
- any limitations that still require human review.

## Safety rules

- Never overwrite input, expected-output, or production files unless the user
  explicitly requests it and the target is unambiguous.
- Work only on anonymized samples when possible.
- Do not silently repair unrecognized layouts.
- Do not infer a column solely from its current letter if the specification says
  it is identified by header.
- Do not convert formulas to cached values.
- Do not convert native dates or numbers to text just to change their display.
- Do not declare completion without inspecting test/report results.

## Current core-engine limitations

As of the current `excel-framework-core` implementation, its comparator detects
sheet-name/order changes, column-count and header changes, formula differences,
number-format differences, and merged-cell differences.

It does **not** comprehensively compare ordinary non-formula cell values, fonts,
fills, borders, alignment, widths, heights, hidden state, hyperlinks, comments,
tables, filters, validation, conditional formatting, frozen panes, names, charts,
or metadata. `ignored_properties` is parsed but not applied.

Therefore:

- never claim that the current generic report proves the workbook is identical
  outside allowed ranges;
- add task-specific assertions for all important invariants;
- manually inspect representative outputs in Excel or LibreOffice;
- improve `../excel-framework-core` when comprehensive generic checking is
  required.

## Definition of done

A transformation is complete only when:

- the specification is precise and matches the implementation;
- allowed changes are narrowly documented;
- the generated workbook matches the approved expected output for all relevant
  business rules;
- formulas and native data types have the intended semantics;
- unrelated high-risk content is covered by direct tests or documented manual
  inspection;
- all applicable tests pass;
- production execution and quarantine behavior are documented;
- routine runs require no LLM interaction.
